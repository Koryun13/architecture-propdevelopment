## 2. Какие разделы включены в проверочный лист и почему

Разделы выбраны по проблемам и приоритетам компании: нарушен контроль данных, есть проблемы с API партнёров, жалобы на чужие ФИО в личном кабинете, планируются продукты на BI, ML и AI, после утечки у конкурента есть риск инцидента, нужно проверить соответствие законодательству РФ (152-ФЗ).

| Раздел | Включён | Обоснование |
|---|---|---|
| I. Управление доступом | Да, полностью | В компании несколько контуров учётных записей (Keycloak, два Active Directory, auth-db-1 в финансах) и нет единого реестра. Доступ аналитиков к DWH не ограничен, а партнёр одной УК видит данные другой. Это прямые нарушения принципа минимальных привилегий. |
| II. Безопасность данных | Да, полностью | Это ключевая проблема компании (см. Task1). Нужно проверить классификацию, шифрование, учёт ПДн, Data Governance, качество и целостность (дубли клиентов, чужие ФИО), обезличивание перед передачей в DWH и BI/ML, а также резервное копирование. |
| III. Защита инфраструктуры | Да, полностью | Гибридная инфраструктура (ЦОД, приватное облако, облачный провайдер) и внешний доступ клиентов и партнёров. Есть firewall, но нужно проверить сегментацию, фильтрацию между сегментами, сканирование уязвимостей и облачных ресурсов, которые команды поднимают самостоятельно. |
| IV. Управление инцидентами | Да, полностью | Утечка у конкурента и требования 152-ФЗ об уведомлении Роскомнадзора об инциденте с ПДн (24 и 72 часа). Специалист по ИБ один на компанию, поэтому без SIEM, оповещений и плана реагирования инцидент обнаружат поздно. |
| V.1. Специфические аспекты: общие вопросы | Да | Сотрудники и подрядчики работают удалённо и с облачными ресурсами, а резервные копии в облаке нужно проверить отдельно. |
| V.2. Управление оборудованием и физическая безопасность | **Нет** | Проблем с физической безопасностью в описании нет, данных для заполнения тоже. Аудит ЦОД — отдельная задача, которую не стоит смешивать с приоритетами текущего аудита (данные и интеграции). |
| VI. Интеграции и API партнёров (добавлен) | Да | Вторая глобальная проблема компании: API управляющих компаний и поставщиков без единых политик, контракты отдают ПДн, нет изоляции данных между УК (multi-tenancy). Компания планирует расширяться за счёт партнёрских сервисов, например «Умного дома» (Task3). Шаблонных вопросов для этого не хватает. |
| VII. Организация ИБ и управление изменениями (добавлен) | Да | Специалист по ИБ один, после смены руководителей ему передают не все решения и изменения. Нужно проверить процесс согласования изменений с ИБ, ответственных за безопасность в командах и соответствие 152-ФЗ (уведомление Роскомнадзора, согласия, модель угроз). |

## 3. Основные выводы по заполненному листу
1. **Управление доступом** — нет единого реестра и централизованного управления учётными записями, принцип минимальных привилегий не соблюдается (DWH, API партнёров). Рекомендуется единый IdP/SSO (Keycloak с федерацией Active Directory), RBAC и ABAC, MFA для сотрудников и регулярный пересмотр прав.
2. **Безопасность данных** — нет политики классификации, Data Governance, единой точки регистрации клиента (MDM) и обезличивания при передаче в DWH. Отсюда ошибки в личном кабинете и блокировка BI, ML и AI.
3. **Интеграции** — нужен API Gateway с единой политикой безопасности: OAuth 2.0 и mTLS, изоляция данных по УК, минимизация ПДн в контрактах, аудит обмена.
4. **Инциденты и процессы** — нужны SIEM, план реагирования, обязательное согласование архитектурных изменений с ИБ и Security Champions в продуктовых командах.
