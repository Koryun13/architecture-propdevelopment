# Требования к внешним интеграциям: сервисы «Умный дом»

Требования относятся к интеграции PropDevelopment с платформой партнёра: интеллектуальным домофоном и интеллектуальным шлагбаумом.
Они также становятся общим стандартом для всех партнёрских интеграций компании (УК, поставщики ЖКУ, платёжная система), которые поэтапно переводятся на `partner-api-gateway`.

## 1. Классификация данных интеграции

| Данные | Класс (Task1) | Где хранятся | Передаются партнёру |
|---|---|---|---|
| Биометрический шаблон лица жильца | Секретные (особая категория ПДн, ст. 11 152-ФЗ) | Только у партнёра | Фото при регистрации лица передаётся один раз, по явному согласию, и в PropDevelopment не сохраняется |
| Номер автомобиля и его привязка к квартире | Конфиденциальные (ПДн) | smart-home-db | Да, только номер и ID точки доступа |
| Права доступа (квартира, подъезд, шлагбаум) | Конфиденциальные | smart-home-db | Да, по псевдонимизированному ID жильца |
| Команды открытия и коды доступа | Секретные | Не хранятся, только журнал | Да, команда с одноразовым идентификатором |
| События (вызов, проход, въезд), снимки с камер | Конфиденциальные | Журнал событий smart-home-db, снимки — только у партнёра | От партнёра к PropDevelopment |
| ФИО, телефон, адрес собственника | Конфиденциальные | CRM ЖКУ | **Нет**: партнёр получает только псевдонимизированный `resident_id` |

## 2. Требования к безопасности

### 2.1. Защита канала и периметра
1. Весь обмен с партнёром идёт только через `partner-api-gateway`. Прямые вызовы из сервисов PropDevelopment к партнёру и обратно запрещены сетевыми политиками (Kubernetes NetworkPolicy, см. Task5) и межсетевым экраном.
2. Транспорт — TLS 1.2+ (рекомендуется TLS 1.3), с российскими сертификатами ГОСТ там, где этого требует регулятор. Слабые наборы шифров отключены.
3. Взаимная аутентификация сервер–сервер — **mTLS** с сертификатами, которые выпускает доверенный УЦ PropDevelopment. Срок жизни сертификата — не более 1 года, ротация автоматическая через `secrets-vault`.
4. IP allowlist адресов партнёра для входящих webhook, на внешнем периметре — WAF и защита от DDoS.
5. Канал между платформой партнёра и оборудованием ЖК зашифрован (TLS или VPN). Оборудование размещено в изолированном сегменте сети и не имеет доступа к сетям PropDevelopment.

### 2.2. Защита данных
1. **Минимизация данных**: в контрактах API нет ФИО, телефонов, адресов и паспортных данных. Партнёр получает только псевдонимизированный `resident_id`, ID квартиры или точки доступа и номер автомобиля.
2. **Биометрия**:
   - обрабатывается только при отдельном письменном (электронном) согласии жильца (ч. 1 ст. 11 152-ФЗ), отказ не ограничивает остальные функции: открытие по звонку или из приложения работает;
   - шаблон хранится только у партнёра, PropDevelopment хранит идентификатор профиля и статус согласия;
   - при отзыве согласия или потере права доступа (продажа квартиры, выезд) PropDevelopment отправляет запрос на удаление профиля, партнёр подтверждает удаление в течение 24 часов.
3. **Изоляция данных по ЖК и УК (multi-tenancy)**: каждый запрос партнёра ограничен scope его ЖК. Шлюз и `smart-home-app` проверяют принадлежность объекта (защита от BOLA/IDOR), поэтому партнёр не может получить данные других ЖК или УК.
4. Шифрование хранимых данных: smart-home-db, резервные копии и журналы шифруются (TDE или шифрование томов), ключи хранятся в `secrets-vault` или KMS.
5. Сроки хранения: журнал событий доступа — 1 год, снимки с камер у партнёра — не более 30 дней, затем удаление.
6. Партнёр — обработчик ПДн по поручению PropDevelopment (ч. 3 ст. 6 152-ФЗ). Договор фиксирует цели, перечень данных, меры защиты, локализацию данных в РФ (ч. 5 ст. 18), уведомление об инцидентах в течение 24 часов и право PropDevelopment на аудит.

### 2.3. Целостность и защита от подделки команд
1. Каждая команда открытия содержит `command_id` (UUID), `timestamp` и подпись или привязку к access-токену. Партнёр отклоняет повторы (`Idempotency-Key`, окно ±60 с) — защита от replay-атак.
2. Входящие webhook партнёра подписаны HMAC-SHA256 (`X-Signature`, `X-Timestamp`). Шлюз проверяет подпись, время и уникальность события.
3. Схемы запросов и ответов валидируются на шлюзе по OpenAPI-контракту. Поля, которых нет в контракте, отбрасываются (защита от mass assignment и утечки лишних данных).
4. Открытие двери из приложения требует свежей аутентификации пользователя (биометрия устройства или PIN, step-up) не старше 5 минут.

### 2.4. Доступность и отказоустойчивость
1. Отказ интеграции не блокирует физический доступ: на оборудовании остаются ключ или карта, вызов консьержа или диспетчера. Деградация описывается в SLA.
2. SLA партнёра: доступность API не ниже 99,9%, время открытия по команде — не более 2 секунд (p95).
3. На шлюзе работают rate limiting и квоты (по партнёру и по жильцу), на стороне `smart-home-app` — circuit breaker и таймауты. Повторные попытки доставки webhook — с экспоненциальной задержкой.

### 2.5. Журналирование, мониторинг и реагирование
1. Шлюз и `smart-home-app` журналируют каждый запрос: кто, когда, к какому объекту, результат. ПДн в журналах маскируются. Журналы отправляются в SIEM, срок хранения — не менее 1 года.
2. Алерты: всплеск ошибок 401 и 403, попытки обращения к чужим объектам, команды открытия вне обычного профиля жильца, отказ проверки подписи webhook.
3. Совместный с партнёром регламент реагирования на инциденты: контакты, сроки уведомления (24 часа, как требует 152-ФЗ для Роскомнадзора), порядок отзыва ключей и сертификатов.

### 2.6. Процесс подключения и сопровождения
1. Интеграция вносится в реестр интеграций: владелец, контракт, классы передаваемых данных, сертификаты, сроки ротации.
2. Перед запуском — проверка ИБ: security review архитектуры, проверка контракта на минимизацию ПДн, пентест API по OWASP API Security Top 10. Далее проверки повторяются ежегодно и при каждом изменении контракта.
3. Изменения контракта согласуются со специалистом по ИБ (см. Task2, раздел VII). Версии API (`/v1`, `/v2`) поддерживаются не менее 6 месяцев после выхода новой.

## 3. Протоколы аутентификации и авторизации

| Взаимодействие | Аутентификация | Авторизация |
|---|---|---|
| Собственник → мобильное приложение → `smart-home-app` | **OpenID Connect, Authorization Code + PKCE** через `auth-service-1` (Keycloak). Access token JWT живёт 5–15 минут, refresh token — с ротацией. Для открытия двери — step-up аутентификация (биометрия устройства, PIN или MFA) | **RBAC + ABAC**: роль `resident` или `owner` плюс атрибуты из CRM — квартира, подъезд, ЖК, разрешённые точки доступа. Собственник может выдавать временный доступ членам семьи и гостям |
| `smart-home-app` → `partner-api-gateway` (внутренний вызов) | mTLS внутри кластера (service mesh), сервисный токен Keycloak (OAuth 2.0 Client Credentials) | Scope `smart-home:command`, `smart-home:access-rights`; NetworkPolicy разрешает трафик только от `smart-home-app` |
| `partner-api-gateway` → API партнёра | **mTLS** + **OAuth 2.0 Client Credentials** у сервера авторизации партнёра (или по согласованию — JWT client assertion, RFC 7523). Секреты хранятся в `secrets-vault` | Scope, ограниченный ЖК PropDevelopment: `access.write`, `command.open`, `biometry.enroll` |
| Партнёр → `partner-api-gateway` (webhook) | **mTLS** + **подпись HMAC-SHA256** или OAuth 2.0 Client Credentials токен от Keycloak PropDevelopment | Партнёр может только публиковать события по своим точкам доступа (`events.publish`), читать данные PropDevelopment он не может |
| Видеопоток вызова (партнёр → приложение) | Одноразовый короткоживущий токен (≤ 60 с), который выдаёт `smart-home-app` по запросу аутентифицированного жильца | Токен привязан к конкретному вызову, квартире и пользователю |
| Сотрудники PropDevelopment (диспетчеры, поддержка) | SSO через Keycloak с федерацией Active Directory + MFA | RBAC: просмотр событий и прав доступа только по своим ЖК, без доступа к биометрии и командам открытия |

## 4. Организация взаимодействия между системами PropDevelopment и платформой партнёра

### 4.1. Архитектура
- **Синхронные операции** (REST/HTTPS, JSON, OpenAPI 3) идут через `partner-api-gateway`: выдача и отзыв прав доступа, команда открытия, регистрация лица, запрос токена видеопотока.
- **Асинхронные события** — входящие webhook партнёра (вызов домофона, проход по лицу, въезд по номеру, ошибки оборудования). Шлюз принимает событие, проверяет подпись и сразу отвечает `202 Accepted`. Дальше событие публикуется в Kafka (`smart-home.events`), `smart-home-app` обрабатывает его и отправляет push или WebSocket-уведомление в приложение.
- **Сверка (reconciliation)**: раз в сутки `smart-home-app` сверяет список прав доступа с партнёром (`GET /access-rights?complex_id=...`), чтобы устранить расхождения после сбоев.
- **Источник истины по собственникам** — CRM ЖКУ (`crm-tenant-db`). При изменении собственника (продажа квартиры, выписка) права доступа и биометрические профили отзываются автоматически.

### 4.2. Основные сценарии

**Выдача права доступа и регистрация лица**
1. Собственник в приложении добавляет себя, члена семьи или автомобиль. Для биометрии он подписывает согласие.
2. `smart-home-app` проверяет в CRM, что пользователь — собственник квартиры, и сохраняет право и согласие в `smart-home-db`.
3. `smart-home-app` → шлюз → партнёр: `POST /v1/access-rights` (`resident_id`, `access_point_ids`, `plate_number` или `face_enrollment`). Фото передаётся однократно и в PropDevelopment не сохраняется.
4. Партнёр возвращает `profile_id`, который сохраняется в `smart-home-db`.

**Вызов домофона и открытие по звонку**
1. Гость звонит в домофон. Партнёр отправляет webhook `call.started`.
2. `smart-home-app` определяет жильцов квартиры и отправляет push, а приложение запрашивает одноразовый токен видеопотока.
3. Жилец нажимает «Открыть». Приложение (свежий JWT) → `smart-home-app` → шлюз → партнёр: `POST /v1/access-points/{id}/open` с `command_id`.
4. Партнёр открывает дверь и присылает событие `door.opened`, которое попадает в журнал.

**Автоматическое открытие по лицу или номеру автомобиля**
1. Партнёр распознаёт лицо или номер, сверяет со своим списком прав, открывает дверь или шлагбаум и присылает событие `access.granted` или `access.denied`.
2. `smart-home-app` журналирует событие и при необходимости уведомляет жильца, например о въезде автомобиля.

**Отзыв доступа**
При продаже квартиры, удалении члена семьи или отзыве согласия выполняется `DELETE /v1/access-rights/{id}` и `DELETE /v1/biometric-profiles/{profile_id}`, а партнёр подтверждает удаление.

### 4.3. Контракт API (основные методы)

| Направление | Метод | Назначение |
|---|---|---|
| PD → партнёр | `POST /v1/access-rights` | Выдать право доступа (жилец, автомобиль, точки доступа, срок действия) |
| PD → партнёр | `DELETE /v1/access-rights/{id}` | Отозвать право доступа |
| PD → партнёр | `POST /v1/biometric-profiles` / `DELETE /v1/biometric-profiles/{id}` | Зарегистрировать или удалить профиль лица по согласию |
| PD → партнёр | `POST /v1/access-points/{id}/open` | Команда открытия (идемпотентная, с `command_id`) |
| PD → партнёр | `POST /v1/calls/{id}/stream-token` | Одноразовый токен видеопотока вызова |
| PD → партнёр | `GET /v1/access-rights?complex_id=` | Сверка прав доступа |
| Партнёр → PD | `POST /webhooks/v1/events` | События: `call.started`, `door.opened`, `access.granted`, `access.denied`, `device.offline` |

Все методы версионируются, контракт фиксируется в OpenAPI. Изменения контракта проходят согласование с ИБ и контрактные тесты (consumer-driven contracts) в CI.
